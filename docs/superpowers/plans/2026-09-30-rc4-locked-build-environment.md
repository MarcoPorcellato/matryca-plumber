# RC4 Locked Build Environment Implementation Plan

> **Execution method:** Subtask-driven implementation with independent reviews; preserve authorization gates.

**Goal:** Make `prepare_sdist_build` consume a preprovisioned, independently bound PEP 517 environment and produce receipts that prove the dedicated lock, environment identity, requirement satisfaction, and package-manifest stability without changing runtime qualification inputs.

**Architecture:** Add a qualification-only build project and lock, separate from root `pyproject.toml` and `uv.lock`. A caller provisions and owns the private environment from that exact lock and supplies a trusted descriptor plus its independently expected digest. The build helper validates and observes the supplied environment; it never creates, resolves, installs, syncs, or repairs it. The receipt aggregator compares descriptor/evidence digests against independently supplied expected bindings.

**Tech Stack:** Python 3.12+, `uv`, PEP 517/518, SHA-256, existing bounded-process and receipt-validation helpers, pytest.

**Spec:** [RC4 independently locked build environment design](../specs/2026-09-30-rc4-locked-build-environment-design.md)

## Global Constraints

- Keep the root runtime/development `pyproject.toml` and `uv.lock` byte-identical. Add only `release-qualification-build/pyproject.toml` and its dedicated `uv.lock` for build requirements.
- The current source declares PEP 518 static build requirements, but no final candidate sdist exists at this planning base. Use static source metadata for the build-project draft; later bind/recheck the exact authenticated sdist before provisioning. Do not execute backend hooks to select lock contents. Dynamic hook requirements are checked at consumption time and must already be present in the locked environment; an uncovered requirement fails closed. If a safe closure cannot be selected from static metadata and reviewed official package data without hook execution, stop and request separate bounded authorization.
- Treat candidate package recommendations as research inputs, not approved versions. Before any lock selection/resolution, recheck official metadata, licensing, advisories, target markers, and artifact hashes for the exact required closure. Do not invent pins or refresh unrelated packages.
- The trusted caller/provisioner owns environment lifetime and retains evidence that it used the reviewed recipe and exact lock, verified locked artifact hashes, and did not re-resolve or repair. `prepare_sdist_build` cannot certify that trust chain. Expected descriptor/evidence digests must come independently from the caller/aggregator; descriptor self-hashing is insufficient.
- The verifier can compare submitted evidence identities to independently supplied expectations; it cannot prove who supplied those expectations or validate evidence it never receives. The caller/aggregator must authenticate the retained provisioning evidence before creating the expected-bindings input.
- Preserve the authenticated original sdist as the installed verifier input, the temporary wheel's name/size/SHA-256 outside canonical `dist`, the existing runtime/test lock and focused runner, and all process/output/time bounds. This is package-set/provenance evidence, not a hostile-code sandbox or same-version-byte immutability proof.
- Keep the Stage A workflow absent and the Windows row NO-GO. Do not alter its admission regression, add/enable/dispatch a workflow, build a package, or claim RC4 qualification. This implementation slice supplies verifier interfaces only; exact-head hosted CI and separate later qualification gates remain required.
- Before Python edits, read the Python standards adapter and its canonical rule. `QUALIFICATION_TEST_PYTHON` means an already-admitted private test-environment interpreter; set it before tests. `QUALIFICATION_UV` means the exact official-verified executable selected for the lock gate. No command below may create/sync the test environment or run a package build.
- Lock generation is a separate resolver action requiring fresh admission, reviewed official metadata, and explicit bounded authorization; it is not implied by this plan. After that gate, check with `rtk proxy "$QUALIFICATION_UV" sync --locked --offline --dry-run --no-python-downloads --python "$QUALIFICATION_TEST_PYTHON" --project release-qualification-build --no-install-project`. This promises no lockfile or project-environment writes; offline mode does not promise no cache or temporary-file writes. Test commands use `rtk proxy "$QUALIFICATION_TEST_PYTHON" ...`, never `uv run`.

## Review Focus

- Can an untrusted or self-generated descriptor be accepted without an independently supplied expected digest and caller-authenticated provisioning evidence?
- Does any helper path create, resolve, install, sync, or repair the supplied environment, or copy one manifest into multiple observations?
- Can a missing, extra, incompatible, or drifting package; target/source/tool/lock mismatch; unsupported marker; legacy receipt; or unbound descriptor pass?
- Are build-lock identity and `provisioning_evidence_sha256` separate from the existing platform runtime `lock_sha256`?
- Is the original sdist still verified unchanged, with exactly one bounded temporary wheel outside canonical `dist`, and is Windows still NO-GO?
