# On-demand cross-platform release package qualification

## Decision and authority

### Astra decision — 2026-09-27

Keep `BundleBinding` unchanged. Require `verify_installed` to receive the exact
installed artifact through a keyword-only `Path`, authenticate its name, size,
SHA-256, and inventory against the independent binding, then derive installed
expectations from bounded parsing of those authenticated bytes. Generated
frontend authority comes from the bound archive, never from Git-only state.
Apply separate, explicit wheel and sdist metadata transformations, and finish
full-file/`RECORD` verification before imports or TCK execution. Use a
site-disabled pre-integrity bootstrap because `-I` alone does not stop `.pth`
startup processing. This decision does not change the Stage A/Stage B boundary
or grant publication authority.

Add a manually dispatched, read-only GitHub Actions workflow for the
pre-publication package and platform evidence required by the
[RC4 qualification plan](../../quality/V2_0_1_RC4_RELEASE_QUALIFICATION_PLAN_2026-09-06.md).
Build one wheel and one source distribution from one exact protected-`main`
commit; verify those same downloaded bytes and their isolated installs on
Linux, macOS arm64, and Windows. Keep ordinary pull-request CI and its required
`Ironclad Gatekeeper` context unchanged.

This workflow supplies evidence for a human Stage A decision. Its green result
cannot create a tag, publish a package, replace Gate B, qualify Logseq DB, or
declare RC4 or stable `v2.0.1` supported. The existing tag-driven
[release workflow](../../../.github/workflows/release.yml) remains the only
publication path and builds its own artifact set after separate authorization.
The Stage A hashes must never be assumed to match those later public bytes.

### Sdist build-environment provenance decision — 2026-09-27

Do not let an installer create an implicit, unrecorded PEP 517 build
environment when qualifying the source distribution. Authenticate the original
sdist against the independent `BundleBinding`, then create a private,
disposable build environment and record its complete observed package-name /
version manifest before and after building. Check static PEP 518 requirements
and every dynamic requirement returned by the backend against packages already
present in that manifest. A malformed, unsupported, missing, or
version-incompatible requirement fails closed; the verification step never
installs a missing dynamic requirement opportunistically.

Run `uv build --wheel --no-build-isolation` against the validated extraction
of the exact original sdist. Record the temporary wheel's name, size, and
SHA-256; require the build-environment manifest to remain unchanged. Install
that temporary wheel with `--no-deps` into the separate clean sdist runtime
environment, but pass the **original bound sdist** to `verify_installed` as
`artifact`. The temporary wheel is an intermediate installation vehicle only:
it stays outside canonical `dist` and never replaces the canonical release
wheel or sdist.

This proves exact artifact bytes and the observed build environment for one
qualification attempt. It does not claim that an independent rebuild would
produce identical wheel bytes or otherwise establish reproducible builds.

Windows launcher provenance and native Windows evidence remain required
NO-GO gates. A deliberately failing Windows step is not a usable qualification
run. Until this gate is resolved, do not dispatch the workflow as a
qualification, claim Stage A PASS, or infer stable-release readiness.

#### Windows launcher research checkpoint — 2026-09-27

that commit's signature as verified. This establishes a useful upstream release
anchor only. The exact tag-to-commit resolution and tag-pinned launcher
source/content path and executable-template provenance used for the generated

is made.

## Why this is needed

At the diagnostic `main` source
`b56254854b28701bd7f8b2e83a8ede58915f309d`, required hosted source CI
was terminal green, a local wheel and source distribution were built, 81 focused
tests passed, and both isolated macOS installs passed all three static TCKs.
An independent review still marked Stage A **BLOCKED**: current CI runs
checkout-based Shadow tests on macOS and Windows, not installed wheel/source
distribution checks there; Linux and Windows installed-package receipts and a
Windows process-lifecycle disposition are missing. That local diagnostic is
bound to its source and does not select or qualify a future candidate.

The repository advertises macOS, Linux, and Windows. The qualification plan
requires candidate-bound package evidence for supported release platforms. No
platform may inherit another platform's pass, and an unavailable row requires
an explicit release decision rather than a silent skip.

## Approaches considered

1. **Selected: separate on-demand workflow.** Build once, share one immutable
   distribution pair with three platform jobs, and run it only for a release
   candidate. This keeps routine PR feedback fast and makes the exceptional
   Stage A run independently inspectable.
2. **Add all checks to required CI.** Automatic exact-head coverage, but every
   ordinary PR pays for three platform installations and another build. It also
   lengthens the existing required gate for work unrelated to release packaging.
3. **Collect ad hoc platform receipts.** No repository change, but scripts,
   environments, source identity, and completeness are harder to reproduce and
   review. This remains a bounded fallback only if the selected workflow cannot
   run; it cannot weaken the RC4 acceptance criteria.

## Workflow and source binding

The new workflow is manually dispatched from the default branch. It accepts
one required, full lowercase 40-character expected commit SHA. An initial gate
checks the input syntax, `github.ref == refs/heads/main`, and exact equality of
the input with `github.sha`; it also verifies that the checkout's `HEAD`, tree,
project version, and clean state match the event. The same immutable SHA is
passed to every job and checked again after checkout. A branch name, moving
ref, tag, PR merge ref, or partial SHA is not a substitute.

The workflow file must first land on protected `main`, because GitHub requires
a manually triggered workflow to exist on the default branch. If introducing
the workflow changes `main`, the previous diagnostic candidate and its local
build evidence become historical. Select the new exact commit, rerun its
ordinary hosted CI, and build/qualify from that commit. If `main` moves again
before the Stage A decision, review applicability and reselect; never relabel
an earlier run as evidence for the new source.

The workflow has no schedule, `pull_request_target`, tag trigger, deployment,
release, package upload, or write-capable token. Its default permissions are
`contents: read`; checkouts use immutable Action pins, explicit source refs,
and no persisted Git credentials. Input values reach shell commands through
environment variables after validation, not direct expression interpolation.

## Build and artifact handoff

One Linux build job runs the repository's existing release builder on a clean
checkout at the selected commit. An optional, out-of-band build-content ledger
records the selected tracked source modules/resources and the frontend files
actually produced before the builder's disposable staging root is removed.
The normal tag-driven builder output remains unchanged. The verifier derives
each archive's expected package-file set from that ledger plus explicit,
reviewed backend metadata rules, and compares exact membership; merely
checking that observed members are allowed would miss omitted code or assets.
It must confirm exactly one wheel and one source distribution, expected
normalized version, archive safety, complete member inventories, and a
two-line SHA-256 manifest. It rejects duplicate or
unexpected distribution files, compiled caches, unsafe archive paths and
member types, and resource or metadata drift. Build logs record source commit,
tree, version, runner identity, filenames, sizes, and digests without secrets
or user data.

The build job independently exports the exact filenames, sizes, and SHA-256
values as validated job outputs. It records the upload artifact ID, digest,
and run ID as handoff identity. The two distributions and manifest are uploaded
as one short-lived workflow artifact. Every platform job downloads that
specific artifact from the same run, rejects unexpected files, and compares
both downloaded distributions against the independent build-job outputs and
the manifest before installation. Thus replacing the distributions *and* the
manifest cannot satisfy the cross-job comparison. An absent, malformed, or
inconsistent output or artifact identity fails closed. GitHub's artifact
transfer digest remains an additional signal, not the sole gate: download
validation can warn. No platform rebuilds the pair or substitutes a PyPI
distribution.

Each platform directly installs the canonical wheel in its wheel environment.
For the sdist lane, a separate private build environment authenticates the
original bound sdist, records its complete exact observed package set, checks
the backend's static and dynamic PEP 517 requirements against that set, and
builds one temporary wheel from the authenticated extraction using
`uv build --wheel --no-build-isolation`. It records the temporary wheel's exact
name, size, and SHA-256 and fails if the build-environment manifest changes.
That wheel is installed with `--no-deps` into the distinct clean sdist runtime
environment. The installed verifier still authenticates and derives its
expected payload from the original bound sdist, not the temporary wheel. The
temporary output never enters canonical `dist`; a one-run hash binding is not
a reproducible-build claim. Package `build_generator` metadata alone does not
prove the complete PEP 517 build environment.

The package verifier checks the complete wheel and source-distribution member
lists against their declared release-source/build outputs, including generated
frontend assets and metadata. It rejects path traversal, links or special
members where not expected, duplicate names, and compiled caches. It compares
the 26 RC4 static contract/TCK resource bytes across source, wheel, source
distribution, and both installations. The verifier checks installed package
name/version, `RECORD` presence, path confinement, and complete installed-file
accounting. It requires verified hashes and sizes for archive-owned payload
and metadata, including all 26 resources and packaged frontend files. The
installed-project specification permits empty hash or size fields: the
verifier therefore defines narrow, auditable exceptions for `RECORD` itself
and identified installer-generated metadata. Fresh, disposable Stage A
qualification environments are deliberately stricter than general installed
packages: every package-owned `.pyc` or `.pyo` fails before import or TCK
execution, even if its path is paired with authenticated source or listed in
`RECORD`. The verifier does not delete or repair such files. Its probes use a
fresh external bytecode-cache prefix so they do not create package-owned
caches during qualification. Other exceptions remain path-confined and
accounted for; they do not excuse missing or unverified distribution payload.
It must prove its negative
checks with synthetic tampered-archive, missing-resource, missing-`RECORD`,
missing-file, extra-file, and malformed-exception fixtures. The verifier
itself is repository source at the qualified commit; a private diagnostic
script is not a hosted qualification authority.

### Installed artifact authority and bootstrap order

The installed verifier requires the exact installed distribution as a
keyword-only `artifact: Path` argument. Before deriving installed expectations,
it authenticates the artifact's exact name, byte size, SHA-256, and member
inventory digest against the corresponding wheel or sdist fields in the
independently supplied `BundleBinding`. It then bounded-parses that authenticated
archive under the same member, per-file, total-size, and metadata limits used by
the archive verifier. `BundleBinding` schema remains unchanged. Generated
frontend bytes and other build outputs come from that authenticated archive;
Git may bind tracked source files, but Git-only frontend state is not authority
for generated frontend payload.

Installed payload expectations use explicit per-format transformations, not a
generic filename guess. For a wheel, package payload paths map directly from
wheel members into the environment's site-packages; the wheel's `.dist-info`
metadata is checked against the authenticated wheel, while installer-created
`RECORD`, `INSTALLER`, `direct_url.json`, and entry-point scripts are handled
only by their narrow documented rules; package-owned bytecode is rejected.
On Windows, generated launcher executables have no archive-derived byte
authority. Until their entire bytes can be verified against an independently
pinned and reviewed installer artifact and architecture-specific template,
including interpreter binding, entry-point payload, and trailing bytes, the
Windows installed-package result is NO-GO. `MZ`, structural PE checks, and a
self-consistent `RECORD` do not suffice. Native Windows x64 evidence for both
installation kinds is required before accepting the platform; no partial pass
or skip substitutes for it. For an sdist, the parser first
requires the exact canonical `<distribution>-<version>/` root and removes that
single prefix from source payload paths before mapping them into site-packages.
The sdist's `PKG-INFO`, `setup.cfg`, and `.egg-info` metadata are build inputs,
not installed payload bytes; installed wheel metadata is therefore accepted
only through the explicit backend/build/install metadata rules and must still
identify the bound project and version. Both paths require installed payload
bytes and metadata inventory to be fully accounted for by `RECORD`; no broad
metadata exemption may cover package code, resources, or frontend files.

Integrity precedes imports and tests. The pre-integrity interpreter bootstrap
uses isolated, site-disabled execution (`-I -S`) so target-environment `.pth`
startup code cannot execute before the environment is verified. `-I` alone
does not disable `.pth` processing. The verifier checks archive-derived
installed-file expectations and complete `RECORD` hashes/sizes first; only
after those checks pass may a separate isolated probe import Plumber and the
three installed TCKs run.

Workflow-contract tests must exercise both passing and failing cases for
dispatch/ref/full-SHA binding, read-only permissions, exactly three required
platform rows, independent build-output versus downloaded-artifact binding,
and the aggregator's failure on skip, cancellation, or any failed dependency.
The tests must verify that no publish-capable path is reachable from this
workflow. A green verifier unit suite alone is not a green workflow contract.

## Platform jobs and focused controls

Use standard hosted `ubuntu-24.04`, `macos-15`, and `windows-2022` runners with
Python 3.12. Record actual OS and architecture, and fail if a runner does not
match the claimed platform. `macos-15` is selected for the arm64 row; a label
alone is not proof of architecture. Linux and Windows are x64 rows. Each job
uses two disposable, isolated runtime environments: one installs the canonical
downloaded wheel; the other installs a temporary wheel produced from the
authenticated original sdist through the separate private PEP 517 build
environment. Resolve runtime dependencies against the selected source's lock
and record their exact versions; neither runtime may import Plumber from the
checkout. The sdist verifier receives the original bound sdist as its artifact
argument. Run all three TCKs from each installed package with isolated Python
execution. Bind the full observed build-environment manifest, dynamic
requirement satisfiers, and temporary-wheel name/size/SHA-256 in the sanitized
sdist receipt. This evidence is exact to that attempt, not a reproducibility
claim.

The Windows row remains required NO-GO until launcher bytes are authenticated
against independently reviewed installer/template provenance and native
Windows x64 package and process evidence is qualified. A workflow that exits
unconditionally on Windows cannot produce Stage A PASS and must not be
dispatched as a qualification.

The focused source tests run on the same exact commit with locked development
dependencies. Linux and macOS run Parser 1.9 snapshot, topology-session,
negative DB-capability, and process timeout/recycle controls. Windows runs the
installed-package/TCK checks and a bounded process-lifecycle test selection;
any unsupported Windows-specific test must be recorded as an explicit
disposition against the RC4 platform claim, not converted to success. Tests
must exercise a controlled timeout and later successful parse, not infer
timeout correctness from fixture speed. All graph fixtures are synthetic; no
user graph, default Logseq root, sync state, or internal Logseq DB is mounted.

The exact test-node list belongs in the implementation plan after confirming
portable test behavior. Test selection cannot silently shrink between review
and dispatch. A change to the selection changes qualified source and requires
a fresh candidate run.

## Result, failure, and evidence rules

Use `fail-fast: false` for the platform matrix so one failure does not hide
other results. A final aggregator runs even after job failure and accepts only
success from source binding, build, and every required platform child. Failure,
cancellation, timeout, unexpected skip, missing artifact, digest mismatch, test
collection error, missing dependency, or incomplete receipt means **NO-GO**.
The job must never use `continue-on-error` to turn a required failure green.

Record the workflow/run URL, event SHA/ref, job names and terminal conclusions,
runner OS/architecture, artifact filenames/sizes/hashes, archive inventory
digests, installed metadata and `RECORD` results, TCK results, selected test
counts, and any explicit platform disposition in a sanitized Stage A evidence
record linked from issue #582. Public evidence excludes local paths, raw graph
content, tokens, private logs, and workstation state. Raw failed output remains
in the hosted run according to repository retention; never replace a failure
receipt with a later pass. A rerun is a distinct attempt with its own run ID.

An independent reviewer reconciles this evidence with the ordinary exact-head
hosted CI, release notes, destination emptiness, and all RC4 plan rows. Only a
separate Stage A GO can precede a separately authorized signed tag and
experimental publication. The public workflow-built bytes then require their
own post-publication verification and dual-profile Gate B campaign.

## Acceptance criteria

- The on-demand workflow remains separate from required PR CI and cannot
  publish or mutate repository/release state.
- A wrong ref, moving or malformed SHA, dirty checkout, unexpected runner,
  artifact change, archive member, missing `RECORD` entry, or any platform
  failure produces terminal failure.
- Exactly one canonical artifact pair is built. The verified canonical wheel
  is installed directly. On each platform, the exact original bound sdist is
  transformed into a temporary wheel in a private PEP 517 environment and that
  temporary wheel is installed in a separate clean sdist runtime environment;
  `verify_installed` receives the original sdist artifact for independent
  binding and payload derivation.
- Every sdist receipt binds the complete observed build-environment manifest
  before and after, static and dynamic requirements with observed satisfiers,
  and temporary-wheel name, size, and SHA-256. Any mismatch or environment
  drift fails closed. Do not claim reproducible builds.
- Each installed verifier authenticates its exact wheel or sdist against the
  unchanged independent `BundleBinding` before deriving archive-based
  expectations; integrity checks run before imports or TCK execution.
- All 26 resource bytes and all three installed TCKs pass in both environments
  on each platform. Parser/topology/timeout controls and Windows lifecycle
  disposition satisfy the RC4 plan without borrowed evidence.
- Windows launcher provenance and native package/process evidence are admitted.
  While they remain NO-GO, the workflow is not dispatchable for Stage A and no
  Stage A PASS or stable-release claim can be made.
- The run emits sufficient sanitized, exact-commit evidence for independent
  Stage A review, while Stage B and stable-support claims remain blocked.
