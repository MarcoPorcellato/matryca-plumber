## Draft

When I wrote [*The Agentic Memory Dilemma: Mem0 vs. Matryca Plumber and the Future of Human-AI Collaboration*](https://www.marcoporcellato.it/agentic-memory-mem0-vs-matryca-plumber/), I was trying to describe a decision that sits underneath the usual feature comparison.

The important question is not simply whether an agent can remember something. It is:

> Who owns the memory, what is the unit of knowledge, and what happens when a human and an agent disagree?

That question has now led to a concrete milestone. Matryca Plumber v2.0.0 is stable and available on [GitHub Releases](https://github.com/MarcoPorcellato/matryca-plumber/releases/tag/v2.0.0) and [PyPI](https://pypi.org/project/matryca-plumber/2.0.0/).

This release does not try to turn a Logseq graph into an opaque AI database. It makes the graph safer and faster to use as a shared cognitive workspace.

## From extracted memories to a shared workspace

Systems such as Mem0 are valuable when an application needs a service that extracts memories, stores them, and retrieves them across sessions. Matryca Plumber addresses a different boundary.

Its canonical memory is the human-readable Logseq Markdown graph. The agent does not receive ownership of a second, hidden representation. It receives a controlled interface to the same knowledge that the human can open, edit, link, version, export, and preserve independently of the model provider.

This distinction changes the engineering priorities. Retrieval quality still matters, but so do provenance, conflict handling, write authorization, rollback, and the ability to understand what happened without trusting a hidden store.

## The block is the unit of trust

Logseq's outliner gives Matryca a particularly useful primitive: the block.

A block can have a durable `id::` UUID, properties, children, links, and an exact position in a page. That makes it both human-readable and machine-addressable. When an agent has a reliable block anchor, Matryca can retrieve the block, a bounded subtree, or a specific heading instead of treating the entire page as an undifferentiated prompt.

That is important for three reasons:

1. **Fewer irrelevant tokens.** A targeted read can carry only the local context needed for the task.
2. **More precise operations.** An agent can append below a parent or update permitted properties inside a known span.
3. **A smaller failure surface.** A mistaken operation has a narrower scope, and stale writes can be rejected through dry-run, locks, and optimistic concurrency control.

This is not a claim that every other memory system is page-based, nor that every Matryca query avoids reading a page locally. A Markdown fallback may scan a page to locate a block. The architectural difference is that the model-facing contract can preserve the block as the canonical unit the human sees and edits, instead of requiring a separate extracted record to become the new source of truth.

## Shadow DB: speed without surrendering authority

The stable v2 release adds a daemon-owned external Shadow DB for fast reads. It uses SQLite FTS5 and bounded hierarchical queries to accelerate search and subtree access, while keeping the cache disposable and rebuildable.

The word *external* matters. The Shadow DB is resolved outside the Logseq graph, so its SQLite, WAL, SHM, and lock files do not become unexpected graph content. Logseq Markdown remains authoritative. Shadow maintenance cannot rewrite a Markdown page or roll back an authoritative write.

The default is now practical rather than ideological: when Shadow is enabled and healthy, reads can use it. When it is disabled, bootstrapping, stale, schema-incompatible, or unhealthy, Matryca fails closed to Markdown-backed BM25 and repository reads. The fallback is part of the contract, not an emergency afterthought.

## Read Only is not a slower version

Strict Read Only is a graph protection boundary. With `MATRYCA_READ_ONLY=true`, graph-local mutation is blocked, but a validated external derived cache can still be maintained.

This makes a useful default profile possible for people who want fast agentic reading without granting an agent permission to change their notes. It also separates two decisions that are often coupled unnecessarily:

- may the system write the user's knowledge graph?
- may the system maintain disposable derived state that improves reading?

Matryca v2.0.0 answers those questions independently. A user can keep the graph read-only and still benefit from the Shadow read path.

## A gardener, not an invisible author

Matryca Plumber can do more than retrieve. Its maintenance modules can consolidate entities, improve properties, repair dangling links, and strengthen connections between notes. But those capabilities are permissioned and graduated.

Safe Mode keeps the most conservative boundaries. Augmented Mode can add link and backlink context. Surgeon Mode can alter original bullet text or restructure dense subtrees and should be used explicitly on a cloned graph first.

The point is not to make the agent passive. It is to make its initiative legible, bounded, and reversible enough that the human remains the owner of the garden.

## What v2.0.0 proves — and what it does not claim

The stable release was promoted only after the corrected RC2 artifact completed dual-profile Gate B qualification, the upgrade and rollback matrix, the RC observation window, cross-platform checks, clean artifact verification, and the release workflow.

That evidence supports a focused claim: Matryca Plumber v2.0.0 is a stable local-first Shadow read path for Logseq OG, with Strict Read Only compatibility and Markdown authority.

It does not claim that biological memory, native Logseq DB writes, proactive adaptation, or every future memory capability is already solved. Those remain separate programmes with their own contracts and qualification gates.

## The direction from here

The larger ambition is still the same one described in the previous article: human and AI should be able to collaborate on durable knowledge without forcing the human to surrender custody of it.

The v2.0.0 milestone makes that ambition concrete. It gives the agent speed through a disposable derived cache, precision through Logseq blocks, and safety through explicit authority boundaries. The result is not a memory service that hides the graph from its owner. It is a shared workspace in which the human-readable graph remains visible, portable, and in charge.
